wlink — WCH-LinkRV Protocol Reference

wlink Documentation

This site is the documentation for wlink, the command-line flash and debug tool for WCH-Link probes and WCH RISC-V MCUs.

Its main part is a protocol reference for the WCH-LinkRV USB protocol — the private protocol spoken between the host and the WCH-Link probe. The old protocol.md at the repository root was written in 2023 and had stopped tracking the implementation; this reference is rebuilt from the source code so that the byte-level description and src/commands/ cannot silently diverge.

This is a reverse-engineered description, not an official WCH specification. WCH does not publish a protocol specification for the WCH-Link. Everything here comes from reading wlink’s implementation, from USB captures, and from other open-source implementations listed in External References. Entries marked unverified are observations only.

Overview and Status

The WCH-Link probe exposes a vendor-specific USB bulk protocol. There is no public specification from WCH; this reference documents the protocol as implemented by wlink, which was reconstructed from USB captures, WCH’s toolchain, and other open-source implementations.

Status of this document

This reference replaces the repository-root protocol.md. That file was last updated in November 2023 and had fallen behind the implementation — it had an empty 0x01 section, two empty DMI tables, a dozen ??? markers, listed 0x0c as unknown (it is SetSpeed), omitted 0x11 entirely, listed only 7 chip families (there are now 28), and stopped at firmware v2.8.

The tables in this reference are derived from the current source on main. Every command page names the Rust symbol that implements it. Anything that could not be confirmed from the implementation is collected in Unverified Commands and Captures and marked unverified rather than guessed.

If you find a mismatch between this document and the code, the code is correct and the document needs a PR.

All multi-byte integers in command payloads are big-endian. Memory read data from the data endpoint is an exception: wlink reverses every 4-byte word after reading it (see Operation Flows).

Layer model

Host (wlink CLI)
  │
  ├─ Command endpoint (0x01 OUT / 0x81 IN)
  │    81 CMD LEN PAYLOAD   →   82 CMD LEN PAYLOAD
  │    all control, configuration and DMI operations
  │
  ├─ Data endpoint (0x02 OUT / 0x82 IN)
  │    unframed bulk stream: flash algorithm blobs, firmware bytes, memory dumps
  │
  └─ DMI operations (command 0x08)
        └─ RISC-V Debug Module registers (0x04 … 0x40)
  • USB Transport describes the device, interfaces and endpoints.
  • Frame Format describes the command frames.
  • Command Reference lists every command ID and payload.
  • Control Subcommands expands the multi-purpose 0x0d command.
  • DMI and the Debug Module covers the debug layer above command 0x08.

Known limitations of the protocol itself

  • LEN is a single byte. wlink reads responses into a 64-byte buffer, so a response payload is limited to 61 bytes in practice; large transfers always go through the data endpoint.
  • The response parser does not check that the response CMD byte matches the request; it only distinguishes the 0x82 success marker from the 0x81 error marker.
  • Error frames carry an opaque one-byte REASON. Only 0x55 (failed to connect to the target) has a known meaning.
  • Some subcommands were observed only in captures from WCH’s Windows utility; they are listed separately as unverified.

  • External References — WCH manuals, schematics, firmware archives and other FOSS implementations.

USB Transport

WCH-Link uses USB bulk transfers. On Linux/macOS wlink opens the device with nusb, claims interface 0, and reads and writes bulk endpoints directly. Windows additionally has two vendor-specific backends that are tried before nusb; see Windows driver backends.

Source: src/probe.rs (constants), src/usb_device.rs (backend selection), src/usb_device/wch_link_driver.rs (native Windows driver protocol).

USB identifiers

ModeVIDPIDNotes
RV (RISC-V debug/flash)0x1a860x8010The mode wlink operates in
DAP (ARM SWD)0x1a860x8012wlink refuses to flash in this mode

The same physical probe appears under one PID or the other depending on its mode. wlink mode-switch flips between them.

Endpoints

EndpointDirectionPurpose
0x01OUTCommand frames (81 CMD LEN PAYLOAD)
0x81INCommand responses (82 … / 81 …)
0x02OUTData endpoint: flash algorithm blob, firmware chunks
0x82INData endpoint: memory dump, per-chunk write acknowledgement
0x02OUT (DAP mode only)Raw mode-switch frame

Command reads use a 64-byte buffer; a single bulk read is treated as one response frame. Data-endpoint transfers are streams, not frames: wlink loops over 64-byte bulk reads until the requested byte count is reached, and pads the final written chunk with 0xff to the family’s data packet size.

The nusb backend stores a 5-second default in NusbDevice::timeout; the current bulk read/write calls do not apply it and rely on nusb’s own blocking behaviour.

Windows driver backends

On Windows, wlink tries these backends in order and uses the first one that can open a probe with the requested VID/PID:

  1. the legacy WCHLinkDLL.dll (CH375) DLL — 32-bit builds only;
  2. WCH’s native driver (WCHLinkDrv / WCHLinkW64.SYS) — 64-bit Windows (x64 and ARM64). The backend is compiled for x86 too, but WCH ships no 32-bit build of that driver;
  3. WinUSB via Zadig, through nusb — all platforms.

The native and WinUSB backends are not interchangeable at the USB level. A probe bound to WCH’s native driver is not a WinUSB device: nusb can still enumerate it and read its USB serial number, but opening interface 0 fails with incompatible driver is installed for this interface. wlink list therefore reports one view (the first backend that finds probes), and the ambiguous-probe guard counts probes visible to the native driver as well.

Native driver IOCTL

The driver installer registers a device interface class {F8D5EDCA-B647-4E9C-9BD3-A5BD2328D55C}. wlink enumerates present interfaces with SetupDiGetClassDevsW / SetupDiEnumDeviceInterfaces, resolves each path with SetupDiGetDeviceInterfaceDetailW, and opens it with CreateFileW. Every descriptor query, bulk read, bulk write and timeout goes through a single vendor DeviceIoControl (0x00223CDC, METHOD_BUFFERED) on that handle — there are no bulk USB transfers in this backend.

There is no public specification for this interface; the layout below comes from observed driver behaviour, originally proposed in #116. Request and response share one buffer, with an 8-byte header in front of the response:

OffsetSizeMeaning
0..4u32Command word. For bulk transfers byte 0 is the endpoint index (USB address minus 1) and byte 2 is 0x01 (read) or 0x02 (write)
4..8u32Payload length; on a read the driver replaces it with the number of bytes returned
CommandHeaderPayloadPurpose
GET_DESCRIPTOR(Device)0x04, 88-byte USB setup packet (80 06 00 01 00 00 12 00)Returns the 18-byte device descriptor, used to match VID/PID
bulk readendpoint, 0x01, lengthresponse onlyReads from a bulk IN endpoint
bulk writeendpoint, 0x02, lengthbytes to writeWrites to a bulk OUT endpoint
SET_TIMEOUT0x0F, 0x10four u32 millisecond valuesSets the driver’s timeouts

The driver exposes no USB serial through this interface, so native-driver (and CH375) probes can only be selected by index. See Selecting a probe: a -d 1a86:8010:<SERIAL> selector requires WinUSB; with either vendor driver use -d <INDEX> instead.

Selecting a probe

With several probes attached, enumeration order is not stable. wlink accepts either an index or a USB serial number:

wlink list
# <WCH-Link#0 nusb device> ID 1a86:8010 Serial F93D8F067E10 (USB-FS 12 Mbps) (RV mode)
# <WCH-Link#1 nusb device> ID 1a86:8010 Serial D7708F065C7F (USB-FS 12 Mbps) (RV mode)

wlink -d 1a86:8010:D7708F065C7F status   # probe-rs style VID:PID:SERIAL
wlink -d D7708F065C7F status             # serial alone
wlink -d 1 status                        # legacy index

Serial matching is case-insensitive and works in either RV or DAP mode; the VID/PID in the selector are validated but not used for matching. A serial selector requires a WinUSB/libusb driver, since the Windows vendor backends cannot open a device by serial; a mistyped serial never falls back to an index.

Switching from RV to DAP mode sends a command frame on the normal command endpoint:

Frame Format

Every command exchange uses the command endpoints (0x01 OUT / 0x81 IN). The data endpoints are a separate, unframed stream.

Source: Command::to_raw and Response::from_raw in src/commands/mod.rs, and WchLink::send_command in src/probe.rs.

Request

Byte 0Byte 1Byte 2Bytes 3 … n
0x81CMDLENPAYLOAD
 
#![allow(unused)]
fn main() {
let mut bytes = vec![0x81, Self::COMMAND_ID, 0x00];
bytes.extend(self.payload());
bytes[2] = bytes.len() as u8 - 3;   // LEN = PAYLOAD.len()
}

LEN is a single byte holding the payload length, so the format allows up to 255 payload bytes. In practice wlink reads responses into a 64-byte buffer, which caps a response payload at 61 bytes; all implemented commands use far smaller payloads.

Example — GetProbeInfo (0x0d, subcommand 0x01):

81 0d 01 01
^^ ^^ ^^ ^^
|  |  |  └─ PAYLOAD[0] = 0x01 (GetProbeInfo)
|  |  └──── LEN = 1
|  └─────── CMD = 0x0d (Control)
└────────── request marker

Success response

Byte 0Byte 1Byte 2Bytes 3 … n
0x82CMDLENPAYLOAD

The parser checks resp[0] == 0x82, verifies LEN == resp[3..].len(), then hands resp[3..] to the response type. It does not verify that CMD matches the request.

Example — GetProbeInfo responding with firmware 2.15 on a WCH-LinkE:

82 0d 03 02 0f 02
         ^^^^^^^^^^ PAYLOAD = [0x02, 0x0f, 0x02]

Error response

Byte 0Byte 1Byte 2Bytes 3 … n
0x81REASONLENPAYLOAD

An 0x81 first byte means failure regardless of CMD. wlink validates the length and surfaces Error::Protocol(reason, response_bytes).

REASONMeaning
0x55Failed to connect to the target RISC-V chip
otherOpaque; the full frame is preserved in the error

Data endpoint stream

The data endpoints carry no 81/82 header. Two shapes occur:

  • Bulk output: the flash algorithm blob for the chip family, then firmware data split into write_pack_size chunks, each padded with 0xff to data_packet_size (see WchLink::write_data_with_progress).
  • Bulk input: read_data(n) accumulates 64-byte bulk reads until n bytes are collected. During a fast-program cycle, each written chunk is followed by a 4-byte acknowledgement on 0x82; wlink checks that the last byte is 0x04 (observed 41 01 01 04).

ProbeSession::read_memory reverses each 4-byte word of the returned memory buffer to compensate for the probe’s word order.

0x0d — Control

The multi-purpose control command. Its first payload byte selects a subcommand; the remainder depends on it. See Control Subcommands for the complete table.

Quick reference: 0x01 probe info, 0x02 attach chip, 0x04/0x05 ROM/RAM split, 0x08 erase by RST pin, 0x09–0x0c power output, 0x0e RST pin, 0x0f erase by power-off, 0xee SDI print, 0xff detach.

0x0e — DisableDebug

Payload 0x01, response (). Only used for specific riscvchip families (older notes mention families 2 and 3). Frame: 81 0e 01 01.

Source: DisableDebug.

0x11 — GetChipInfo / ESignature

PAYLOAD[0]Rust variantNotes

0x06GetChipInfo::V2Introduced in firmware v2.9

This command does not use the standard response frame — see Chip Info and ESIG for the raw 20-byte layout. Source: GetChipInfo, ESignature.

0xff — Mode switch

RawCommand<0xff> with payload 0x41 (81 ff 01 41) switches an RV-mode probe into DAP mode. The reverse direction writes 81 ff 01 52 raw to endpoint 0x02 while the probe is in DAP mode. See USB Transport.

Length caveat for 0x0f

The captured frame from WCH’s utility is:

81 0d 01 0f 09
   ^^ ^^ ^^ ^^
   │  │  │  └─ chip family (0x09 = CH32V003)
   │  │  └──── SUB = 0x0f
   │  └─────── LEN = 1   ← inconsistent: two payload bytes follow
   └────────── CMD = 0x0d

LEN is wrong in the capture. wlink assembles the frame from its own to_raw, producing 81 0d 02 0f 09 with the correct length. Treat the captured length byte as a firmware quirk, not as the protocol rule.

Special-erase operations

0x08 and 0x0f bypass chip attach entirely: the probe performs the erase without a debug connection, which is useful when read protection or a broken auto-detect prevents attaching. Because no detection happens, the caller must supply the chip family:

wlink erase --method power-off --chip CH32H41X
wlink erase --method pin-rst   --chip CH32V003

The riscvchip argument is the one-byte family code from Constants.

SDI print

0xee enables the probe’s virtual serial port used by WCH’s SDI print feature. Captures also show 81 0d 02 ee 00 / 02 / 03 labelled SetSDLineMode; this three-value form is unverified and not implemented by wlink. wlink only uses ee 00 (enable) and ee 01 (disable).

Session lifecycle

A typical session opens with 0x01 (probe info), then 0x02 (attach), runs operations, and ends with 0xff (OptEnd). wlink sends OptEnd on detach unless --no-detach is given; commands that leave the MCU halted deliberately skip detach so the halt is preserved.

Firmware version encoding

The probe does not report a decimal version. Its two bytes are a packed value, and WCH’s tooling displays versions as major * 10 + minor. This is why README says “firmware version 2.15 is actually v35”.

For raw bytes (major, minor):

packed        = 16 * major + minor
version_code  = if packed < 0x30 { 10 * major + minor } else { packed - 12 }
display       = (packed >> 4, packed & 0x0f)

version_code is monotonic and is what wlink uses for all comparisons. display_version reconstructs the human-readable version by treating the packed value as two nibbles, so an “impossible” minor carries into the major.

Chip Info and ESIG

Two commands identify the attached MCU: 0x0d / 0x02 (attach) returns the chip family and ChipID, while 0x11 returns the “ESIG” block with flash size, UID and a second ChipID field.

Sources: AttachChipResponse in src/commands/control.rs, GetChipInfo / ESignature in src/commands/mod.rs, and src/chips.rs for the ChipID database.

0x0d / 0x02 — AttachChip

Request: 81 0d 01 02.

Response payload must be exactly 5 bytes:

OffsetSizeField
01riscvchip — chip family code, decoded via RiscvChip::try_from_u8
1–44chip_id (u32_be), 0 when not reported

Example: 82 0d 05 05 20 36 05 10 → family 0x05 (CH32V20X), ChipID 0x20360510.

ProbeSession::attach retries this command up to 3 times with a 100 ms delay because a freshly powered target can fail the first attach. When --chip is given, the returned family must match or wlink raises ChipMismatch.

The ChipID-to-part-name table lives in src/chips.rs (chip_id_to_chip_name); the per-family tables in the Chip Notes section of this site list the known part numbers.

0x09GetChipInfo::V1Firmware older than v2.9 (version_code < 29)
0x06GetChipInfo::V2Firmware v2.9 and newer

This command does not follow the standard 82 CMD LEN PAYLOAD response format. ESignature overrides Response::from_raw and reads a raw 20-byte buffer directly, with no 0x82/0x81 marker validation. This is tracked in wlink#58.

Observed raw response (from a source comment in src/commands/mod.rs):

ffff 0020 aeb4abcd 16c6bc45 e339e339 20360510
^^^^ ^^^^ ^^^^^^^^ ^^^^^^^^ ^^^^^^^^ ^^^^^^^^
 │    │    │        │        │        └─ ChipID (0x20360510)
 │    │    │        │        └────────── erased-flash pattern 0xe339e339
 │    │    │        └─────────────────── UID words 1 and 2 (see byte order below)
 │    │    └─────────────────────────── flash size in KB (0x0020 = 32 KB)
 │    └──────────────────────────────── prefix / header, meaning unverified
 └───────────────────────────────────── prefix / header, meaning unverified

ESignature::from_raw only parses the first 12 bytes:

OffsetSizeField
2–32flash_size_kb (u16_be)
4–74UID word 1 (u32_be)
8–114UID word 2 (u32_be)

The trailing 8 bytes (erased-flash marker and ChipID) are observed but not parsed by wlink; their semantics are unverified.

UID byte order

wlink stores the two u32_be words and reinterprets them as native-endian bytes for display, producing the same order as wchisp:

words:  aeb4abcd  16c6bc45
bytes:  cd ab b4 ae 45 bc c6 16
UID:    cd-ab-b4-ae-45-bc-c6-16

Erased flash-size field

0xE339 (per halfword) is what erased flash reads back on these MCUs, not 0xFFFF. When the flash-size field equals ESignature::ERASED_FLASH_SIZE (0xE339), wlink substitutes the family’s fixed flash size (RiscvChip::fixed_flash_size_kb). A programmed value always wins.

Example from a test in src/commands/mod.rs (CH32V407VET): ffff 0240 50ad061a ab33546c e339e339 46700000 → 576 KB, ChipID 0x46700000.

Chip family codes

The one-byte riscvchip code is required by SetSpeed (0x0c), by the special erase subcommands (0x0d / 0x08, 0x0d / 0x0f) and by several per-family behaviours. The complete 28-entry table is in Constants and Chip Families.

Operation Flows

This page describes the order in which wlink issues commands. Implementations live in src/operations.rs and src/probe.rs. Command byte layouts are in Command Reference.

Attach (start of a session)

ProbeSession::attach:

  1. Check that the probe variant supports the requested chip. Without --chip, CH32V103 (0x01) is used as the provisional family.
  2. Loop (up to 3 retries, 100 ms apart):
    • 0x0c SetSpeed with the provisional riscvchip and the selected speed;
    • 0x0d / 0x02 AttachChip — break on success.
  3. If --chip was given, verify the detected family matches; otherwise issue 0x0c SetSpeed again using the detected family.
  4. Run the family-specific post-init hook (RiscvChip::do_post_init).
81 0c 02 01 01      SetSpeed(riscvchip=0x01, High)
81 0d 01 02          AttachChip
82 0d 05 05 20 36 05 10   → CH32V20X, ChipID 0x20360510
81 0c 02 05 01      SetSpeed again with the detected family

The CH32V205 family requires firmware v3.6 (version_code >= 42); older firmware misdetects it as CH32V20X and wlink warns.

Status / chip info

ProbeSession::dump_info:

  1. 0x11 / 0x06 GetChipInfo::V2 when version_code >= 29, else 0x11 / 0x09 GetChipInfo::V1 — see Chip Info.
  2. 0x06 / 0x01 CheckReadProtect → report whether flash is read-protected.
  3. If the family supports it, 0x0d / 0x04 GetChipRomRamSplit → SRAM/CODE split mode.

Querying info halts the MCU. wlink re-enables execution on detach.

Erase (default method)

ProbeSession::erase_flash:

  1. If the family supports flash protection:
    • 0x06 / 0x01 CheckReadProtect; protected → unprotect_flash();
    • if unprotected, 0x06 / 0x04 CheckReadProtectEx; write-protected → unprotect_flash().
  2. 0x02 / 0x01 Program::EraseFlash.
  3. 0x0d / 0x02 AttachChip again to re-establish the session.

Unprotect

ProbeSession::unprotect_flash starts with a fresh attach (0x0d / 0xff OptEnd then 0x0d / 0x02), then:

  1. 0x06 / 0x01 CheckReadProtect; if 0x01, 0x06 / 0x02 Unprotect, reattach, re-check.
  2. 0x06 / 0x04 CheckReadProtectEx; if 0x11, 0x06 02 ff ff ff ff ff ff ff (UnprotectEx(0xff)), reattach, re-check.

wlink deliberately skips Unprotect when flash is already unprotected: the probe firmware mass-erases the option-byte page, destroying USER/Data/WRPR.

Flash programming

ProbeSession::write_flash(data, address):

 1  (optional) unprotect_flash()
 2  0x01 SetWriteMemoryRegion(address, len)
 3  0x02 / 0x05 Program::WriteFlashOP
 4  data EP 0x02: write the family's flash algorithm blob
                  (padded to data_packet_size, see src/flash_op.rs)
 5  0x02 / 0x07 Program::Unknown07AfterFlashOPWritten
    → response must be 0x07
 6  0x02 / 0x02 Program::WriteFlash
 7  for each write_pack_size chunk:
       data EP 0x02: write chunk (0xff-padded to data_packet_size)
       data EP 0x82: read 4-byte ack, last byte must be 0x04
                     (observed 41 01 01 04)
 8  0x02 / 0x08 Program::End

data_packet_size and write_pack_size are per-family; see RiscvChip::data_packet_size / write_pack_size in src/lib.rs.

Memory read

ProbeSession::read_memory(address, length):

  1. Round length up to a multiple of 4.
  2. 0x03 SetReadMemoryRegion(address, len).
  3. 0x02 / 0x0c Program::ReadMemory.
  4. 0x82 data endpoint: read len bytes in 64-byte bulk chunks.
  5. Reverse each 4-byte word to fix the probe’s word order.

A leading A9 BD F9 F3 sequence indicates a read from an invalid location or a chip that has just entered debug mode; wlink logs a warning.

Special erase (power-off / RST pin)

erase --method power-off|pin-rst --chip <FAMILY> bypasses attach entirely:

 0x0c SetSpeed(riscvchip=<--chip>, High)
 0x0d / 0x0f EraseCodeFlash::ByPowerOff    → 81 0d 02 0f <riscvchip>
   or 0x0d / 0x08 EraseCodeFlash::ByPinRST  → 81 0d 02 08 <riscvchip>

Both require a probe with power functions and a chip family whose support_special_erase() is true. Because there is no auto-detection, --chip is mandatory. The RST-pin variant additionally needs the nRST line wired to the target.

DMI and the Debug Module

The Debug Module Interface (DMI) is a separate layer above the WCH-Link command protocol: a single 0x08 command carries one DMI transaction. The register addresses and semantics come from the RISC-V Debug Specification 0.13.2 and WCH’s QingKe debug manuals.

Sources: DmiOp / DmiOpResponse in src/commands/mod.rs, src/dmi.rs, src/regs.rs.

0x08 transaction layout

Request payload (6 bytes):

OffsetSizeField
01addr — DMI register address
1–44data (u32_be), ignored for NOP/READ
51op — 0x00 NOP, 0x01 READ, 0x02 WRITE

Response payload uses the same 6-byte shape; op is now a status:

opMeaningDmiOpResponse helper
0x00Successis_success()
0x02Failedis_failed()
0x03Busy / failedis_busy(), also counted by is_failed()

Example — read DMSTATUS (0x11):

→ 81 08 06 11 00 00 00 00 01
← 82 08 06 11 00 00 00 00 00

dmi_read polls on busy (up to 100 retries with 10 ms sleeps) and raises Error::NotAttached when it sees op == 0x03 && data == 0xffffffff && addr == 0x7d.

Higher-level operations

DebugModuleInterface (implemented for WchLink) provides dmi_nop, dmi_read, dmi_write and typed register helpers. ProbeSession builds on them for:

  • ensure_mcu_halt / ensure_mcu_resume — write 0x80000001 to DMCONTROL (0x10) and poll DMSTATUS;
  • register and memory inspection via abstract commands and the program buffer;
  • dump_regs, dump_core_csrs, dump_pmp_csrs, dump_dmi.

The RISC-V Debug Specification details are out of scope for this project documentation. See External References for the QingKeV2 debug manual and other implementations.

Flash algorithm blobs

Each supported family has a binary “flash OP” blob in src/flash_op.rs, sent over the data endpoint after 0x02 / 0x05 Program::WriteFlashOP. They are opaque byte arrays selected by RiscvChip::get_flash_op, for example CH32V307: [u8; 446], CH32V003: [u8; 498], CH32H417: [u8; 618], CH564: [u8; 1532]. Some families have an _ALT variant. Packet and write chunk sizes come from RiscvChip::data_packet_size and RiscvChip::write_pack_size in src/lib.rs.

Unverified Commands and Captures

This page collects protocol knowledge that wlink does not implement and cannot confirm. It exists so that the old protocol.md’s ??? markers are not silently dropped: they are either resolved (and documented on other pages) or listed here as observations.

unverified means: seen in a USB capture from WCH’s utility, or written in an older note, without a confirmed implementation in wlink. Do not rely on these byte sequences in new code without re-capturing.

Raw captures recorded in the source

Copied verbatim from the comment block at the end of src/commands/mod.rs:

81 0D 05 11 SetAccessAddress
81 0F 01 02 GetDeviceMode
81 0D 01 07 EnableQE
81 0D 01 06 CheckQE
81 FE 01 00 DisEncrypt
81 0D 01 0F ClearCodeFlashB
81 0D 02 08 xx ClearCodeFlash
81 11 01 0D unknown in query info, before GetChipRomRamSplit
81 0D 02 EE 00/02/03 SetSDLineMode
81 0F 01 01 SetIAPMode

Observations:

  • 0x0f appears as a command ID in GetDeviceMode / SetIAPMode captures, not as a “begin verify” 0x02 subcommand as the old document claimed.
  • 0xfe appears once as DisEncrypt.
  • 81 0D 01 0F (ClearCodeFlashB) has LEN = 1 while two payload bytes follow — see the discussion of the analogous 0x0f length quirk in Control Subcommands.
  • 81 11 01 0D is a 0x11 variant not used by wlink, which only sends 0x09 (V1) and 0x06 (V2).
  • 81 0D 02 EE 00/02/03 suggests additional SDI line modes; wlink only uses ee 00 / ee 01.
